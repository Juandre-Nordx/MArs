# V0.4 — Administration and pinned catalogues

V0.4 extends the existing colony simulation. `/admin` provides protected login, catalogue editors, original isometric placeholder art, durable PNG/WebP uploads, draft validation, change previews, atomic publication, history and administrator account controls. It does not implement a new industry simulation.

## Setup

Node 22+, npm 10+ and PostgreSQL 16 are required for administration. Run from the repository root. The API does not load `.env` itself.

```sh
cp .env.example .env
set -a
. ./.env
set +a
PRISMA_SKIP_POSTINSTALL_GENERATE=true npm ci --no-audit --no-fund
npm run db:generate
docker compose up -d db
npm run db:migrate
npm run build
```

Apply migrations explicitly, before enabling admin access, using the deployment database's `DATABASE_URL`. This release adds `202611040001_admin_catalogue` after the original migration. HTTP startup never runs migrations or seeds content. Do not run development fixtures against a production database.

Create the **initial** administrator using a private password prompt in Bash:

```bash
read -rsp 'Initial admin password (12–128 characters): ' mars_admin_password
printf '\n'
printf '%s' "$mars_admin_password" | npm run admin:create -w @mars/api -- admin@example.com
unset mars_admin_password
npm run dev
```

The address above is an example; choose your own administrator address. The command reads the password only from stdin, uses salted scrypt (N=32768, r=8, p=3), and refuses to create another administrator when any administrator exists. It never upgrades an existing player or replaces a password. There is no public registration endpoint. Password changes in **Admin Account** revoke all of that account's sessions. Additional administrator provisioning/recovery requires a separately controlled database/operator workflow; no public recovery service is supplied.

Open `http://localhost:5173/admin`, sign in, then select **Initialise draft from game**. Initialisation is idempotent and preserves existing edits. Use one exact browser origin throughout the session. For `http://127.0.0.1:5173`, set `ADMIN_ORIGIN=http://127.0.0.1:5173` instead of the example's localhost origin.

In production set:

- `DATABASE_URL`: the PostgreSQL connection URL, supplied through Railway variables.
- `NODE_ENV=production`: already supplied by the Dockerfile.
- `ADMIN_ORIGIN=https://your-public-domain`: exact scheme and host, no trailing slash/path. Required for admin writes, including login.
- `ADMIN_UPLOAD_LIMIT_BYTES`: optional, defaults to 2097152 decoded bytes; bounded to 1 KiB–8 MiB. Canonical output must fit too.
- `PORT` and `WEB_ROOT`: retain the existing Railway/Docker configuration.

Production cookies use the `__Host-` prefix, Secure, HttpOnly, SameSite=Strict and an eight-hour maximum age. Sessions expire server-side; role and enabled status are checked on every admin request. Writes require both the trusted Origin and the session's CSRF token. Tokens are random; only token hashes are stored. Responses never expose passwords, password hashes or session tokens. Login is limited to five attempts per IP per fifteen minutes in each process. Multiple replicas require a shared edge/proxy login limiter; this release supplies a process-local limiter and does not trust arbitrary forwarding headers.

## Editor and publication behavior

The sidebar provides Overview, Minerals & Resources, Industry Buildings (including Recipes), Drafts & Publishing, Audit History and Admin Account. Tables search and sort. Editors retain failed edits, show validation/server errors, and warn before discarding unsaved work. Concurrent edits use the overall draft revision: a stale save/publish returns 409 and leaves its form available for review. Reloading a draft requires discarding any unsaved form first.

Resource columns are Icon, Name, Description, Value and Measurement Unit. Value is credits per unit and is metadata: trading is not implemented. Permanent IDs and definition revisions are retained. Definitions are archived, never deleted through the API. New resource/building/recipe entries default to planned and archived. Selecting “implemented” does not add simulation support; the server validates actual supported IDs and behavior.

Building and recipe quantities use catalogue selectors. Electricity is explicitly separate: buildings have their base operating demand; continuous recipes have no additional charge; paid drone recipes add assembly electricity per active tick. A tick is one second, so kW/3600 and MW\*1000/3600 yield kWh per tick. kg, L and items describe different dimensions; kWh describes energy; kW/MW describe rates. Existing core stock/mineral units remain unchanged. Unit conversion, new utility channels, changed footprints and custom equipment require future tested migrations/mechanics and are blocked for active content.

Existing supported building names, descriptions, categories, artwork, construction metal/credits, base electricity, worker requirements and compatible storage capacities are editable. Geometry and utility capability changes are blocked. Starter storage must retain the existing landing cargo. Existing continuous recipes can change rates within their original resource channels, account for their inputs and conserve mass; solar requires explicit sunlight. Existing survey/extraction drone recipes can change metal inputs, assembly duration, power and worker requirements. Fixed queue/fleet limits, road/power requirements, paid charging and deployment restrictions remain in force. Continuous recipe duration is fixed at one tick; unsupported equipment, refining, new products or arbitrary conversions cannot be published active. Finite deposit extraction and scanning retain their existing algorithms and reserves.

Use **Drafts & Publishing → Validate and preview changes**, inspect before/after differences, then **Publish validated revision**. The API revalidates and atomically commits all definitions, recipes and asset references, claims the draft revision and advances the current pointer in one transaction. Failed/conflicting publication leaves the current version untouched. PostgreSQL triggers reject updates/deletes of published snapshots, stored art and audit records. Historical publications and their asset references are retained. Audit records identify the actor, edit target/revisions, upload metadata and publication digest; they contain no credentials.

## Artwork and durability

Separate upload slots accept resource icons, building icons and isometric building sprites. The server checks PNG/WebP magic bytes, decodes the actual image, rejects malformed/animated images and unsupported contents, bounds pixel count and dimensions, and re-encodes a still PNG without metadata. Icons are 16–512 px; sprites are 16–2048 px; maximum decoded image area is 4 megapixels. Safe UUID storage keys replace user filenames. FBX, GLB, ZIP and other model/archive formats are rejected. Authors must supply isometric artwork; image validation cannot determine artistic perspective.

Uploads are PostgreSQL `bytea` records, not container files. Railway needs no upload filesystem volume. Back up **the entire PostgreSQL database including asset bytes and immutable publications**; storage growth and retention are operational responsibilities. Uploaded art is available privately for previews; the public endpoint serves only assets referenced by a published version. Replacement creates a new asset ID; reset selects an original placeholder. There is no destructive asset-delete endpoint. Scale and anchors affect rendering without changing saved building identity, footprint or costs. The game loads uploaded sprite textures once per selected catalogue; unavailable art falls back to original procedural sprites/icons without replacing catalogue behavior.

## Game and saves

`GET /api/catalogues` lists publications; `GET /api/catalogues/current`, `/builtin-v0331` and `/published-N` resolve validated snapshots. Public responses contain only published content. `POST /api/new-game` accepts an optional `catalogueVersion`; the player UI provides a new-colony selector. No version specified means current publication, or original built-in content before first publication. An unavailable database allows a new default colony using the original catalogue **with an explicit warning**. An explicitly selected missing/unavailable version fails rather than substituting another version.

Schema 8 embeds the full immutable validated snapshot with its version ID in each save. Simulation ticks use this in-memory snapshot, never network/database requests. Published edits affect new colonies selecting that version. Existing saves retain costs, units, recipes and production progress, including offline loads. A missing/incompatible embedded snapshot fails clearly; a save is not silently rebound to “current.” Artwork still requires the retained published asset endpoint when its browser cache is empty. Schema 1–7 saves migrate onto the original V0.3.3.1 definitions, preserving their existing state and prior compatibility repairs. Derived network metrics are rebuilt on load as before.

Browser-local saves and the existing player bearer-session verification remain; public player account creation and cloud saves are not implemented. Admin storage failures return 503 while `/api/health`, in-memory simulation and browser saves continue. `/api/ready` remains a separate database check. Direct Node startup, explicit startup diagnostics and the Dockerfile's plain RUN instructions are preserved. No production rollout is included.

## Verification

```sh
npm run db:generate
npm run build
npm test
npm run lint
npm run format:check
npm run test:production
npx playwright install --with-deps chromium
npm run test:e2e -- --workers=1 --timeout=90000
```

Real database tests are enabled with `MARS_TEST_DATABASE_URL`. They deliberately truncate fixtures and accept only a loopback PostgreSQL database named `mars_test` or `mars_v04`. Use a dedicated disposable database, apply migrations first, and run unit tests before browser tests (never concurrently against the same database):

```sh
export MARS_TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:5432/mars_test
DATABASE_URL="$MARS_TEST_DATABASE_URL" npm run db:migrate
npm test
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:e2e -- --workers=1 --timeout=90000
```

Playwright passes that test URL to its API server. Without it, database integration/browser admin cases are explicitly skipped; pure validation, password hashing, outage and existing game tests still run. CI provisions isolated PostgreSQL and runs both suites with database coverage enabled.

The Prisma 6 client uses the official JavaScript PostgreSQL adapter and in-process/WASM generator API, with no native runtime query engine. The migration CLI still needs Prisma's schema engine. In this managed environment its download host returns HTTP 403; TLS/checksum verification has not been disabled. The committed SQL was applied only to the isolated PostgreSQL 16 test container using `psql` for local verification. This is not evidence of a successful production migration or deployment.

Local verification: the production workspace build, all 169 unit/PostgreSQL integration cases, lint, formatting and direct production startup checks passed. All 25 Chromium cases passed, covering the complete admin workflow at 1366×768 and existing gameplay regressions. World performance checks passed; 1,000 simulation ticks with 100 buildings took approximately 0.53 seconds (5-second budget). The final Node 22 container run also passed 161 tests, with the eight PostgreSQL-only cases explicitly skipped there; all eight passed against the separate local PostgreSQL instance.

The repository’s Railway-compatible Docker build failed at npm installation in this managed environment. A separate standard-image npm check reproduced `SELF_SIGNED_CERT_IN_CHAIN`; mounting the managed public CA read-only resolved that check. A clean Node 22 container using that runtime CA mount successfully installed dependencies, generated the JS Prisma client, built all workspaces and passed production startup checks. The session certificate was never copied into the repository/image or added to the deployment Dockerfile. No unsupported secret mounts or disabled TLS checks were added.
