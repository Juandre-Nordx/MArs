# V0.3.3.1 — Independent drone work queues

Based on main `c45213f`, including the V0.3.3 production release. This maintenance revision is displayed as 0.3.3.1; private npm workspace metadata uses valid SemVer `0.3.3+1`.

## Problem and fix

V0.3.3 reserved individual job IDs, but separate survey orders could cover the same tiles. Multiple drones then flew the same survey route despite owning different order IDs. Finished drones also returned home before considering their next queued job.

- Each job has one exclusive drone owner. One active survey also reserves its entire inclusive rectangle across all stations and scan modes; overlapping survey orders wait until that owner finishes.
- Idle drones skip occupied areas and seek the next independent compatible queue. The first matching eligible job is deterministic, and an unaffordable trip does not reserve work that a charged drone could take.
- Completed surveys release their reservation immediately. A finished drone can take another reachable job directly on the next tick if it has enough battery for the trip and return reserve. Full/depleted mines release their worker so it can seek another mine. Spare drones return for charging when no suitable work remains.
- Existing owners retain jobs while travelling, charging or blocked. Miners remain exclusive per mine. Physical travel corridors and charging contacts can still be shared; this change does not introduce vehicle collision avoidance.
- **Survey jobs and drones** now shows the assigned drone for each queue, or an explicit waiting-area / available-drone message. Different nonoverlapping areas can run in parallel.

## Save compatibility and accounting

Save schema remains 7, with schema 1–6 compatibility preserved. Loading existing schema-6/7 surveys with distinct overlapping active orders keeps the first valid owner and requeues the conflicting order(s). Partial cursor/progress, map exploration, discoveries, depleted reserves, drone positions/batteries and material reservations are retained. Invalid duplicate ownership of a single job ID is still rejected, and current-state validation rejects concurrent active overlapping regions.

No resources are generated or refilled by reassignment. Mining still transfers exactly the extracted quantity into local buffers. Existing power, charging, production queues, refunds, fleet limits and central landings remain intact. Dockerfile and Railway startup configuration are unchanged; no database migration or deployment is performed.
